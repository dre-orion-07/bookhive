# 1. Purpose
This document defines the security architecture for BookHive.
It establishes the security principles, authentication model, authorization strategy, data protection mechanisms, API security, and operational practices that every feature must follow.
Security is a core requirement--not an optional feature.
---
# 2. Security Principles
BookHive follows these principles:
- Least Privilege - Defense in Depth - Secure by Default - Zero Trust - Fail Securely - Privacy by Design - Principle of Least Knowledge
---
# 3. Threat Model
Primary threats include:
- Unauthorized access - Account takeover - Token theft - Credential stuffing - API abuse - XSS - CSRF - Injection attacks - Broken access control - Data leakage - File upload attacks - WebSocket abuse - AI prompt injection

--# 4. Authentication Supported methods: - Email & Password - Google OAuth Authentication flow: User  Login  Credential Validation  JWT Issued  Authenticated Session  Protected API Access --# 5. Password Security Passwords must: Minimum 12 characters Be hashed with bcrypt Never be logged

Never be returned in API responses Never be stored in plaintext --# 6. JWT Strategy Access Token Short lifetime Refresh Token Long lifetime Refresh tokens are stored hashed in MongoDB. Revoked tokens are rejected. --# 7. Authorization Every protected resource requires ownership verification. Examples: A user may edit:
 Their profile  Another user's profile
A user may delete:
 Their review  Another user's review
Never trust client-side authorization. ---

# 8. API Security Every endpoint must: Validate request body Validate query Validate params Authenticate user Authorise action Return standardised errors Log security events --# 9. Input Validation All incoming data is validated using Zod. Validation includes: Length Format Required fields Allowed values Data types No controller should receive unvalidated input. --# 10. Output Encoding Escape user-generated content before rendering.

Protect against: Cross-Site Scripting (XSS) Never render raw HTML unless explicitly sanitised. --# 11. Rate Limiting Protect: Authentication endpoints Search AI endpoints Chat Reviews Recommendations Different endpoints may use different limits. --# 12. CORS Policy Allow only trusted origins. Credentials enabled only where required. Reject unknown origins in production. --# 13. Environment Variables Secrets must never be committed. Required secrets include:

DATABASE_URL JWT_SECRET JWT_REFRESH_SECRET GOOGLE_CLIENT_ID GOOGLE_CLIENT_SECRET CLOUDINARY credentials GROK_API_KEY All secrets are loaded through environment variables. --# 14. File Upload Security Uploads are restricted to: Images only Allowed formats: PNG JPEG WEBP Maximum file size enforced. Uploads are scanned and validated before persistence. Store files in Cloudinary. Never execute uploaded files. --# 15. AI Security

Never send: Passwords JWTs Personal identifiers Sensitive metadata to the AI provider. Prompt templates must be controlled by the backend. User prompts should be sanitised to reduce prompt injection risks. --# 16. Database Security Use Prisma ORM exclusively. Never expose raw database queries. Indexes should minimise unnecessary data scans. Database credentials must remain private. --# 17. WebSocket Security Every socket connection requires JWT validation. Validate every event payload using Zod. Verify room permissions before allowing users to join. Disconnect unauthorised clients immediately. --# 18. Logging

Log: Failed logins Successful logins OAuth events Token refreshes Account deletion Suspicious activity Never log: Passwords JWTs Refresh tokens API keys Sensitive personal information --# 19. Error Handling Errors should never expose: Database structure Stack traces Environment variables Secrets Internal implementation details Clients receive generic messages.

Detailed logs remain server-side. --# 20. Security Headers Enable secure HTTP headers including: Content Security Policy (CSP) X-Content-Type-Options Referrer-Policy Permissions-Policy X-Frame-Options Strict-Transport-Security (HTTPS) --# 21. Session Security Invalidate refresh tokens on logout. Support logout from all devices (future). Automatically expire inactive sessions. --# 22. # 1. Purpose
This document defines the testing strategy for BookHive.
The objective is to ensure that every feature is:
- Correct - Reliable

- Secure - Maintainable - Production-ready
Testing is a development activity, not a post-development activity.
---
# 2. Testing Philosophy
BookHive follows these principles:
- Test behaviour, not implementation. - Prefer automated testing. - Prevent regressions. - Keep tests deterministic. - Keep tests fast. - Every bug should result in a new test. - Tests should be readable and maintainable.
---

- Unit Tests: 70% - Integration Tests: 20% - End-to-End Tests: 10%

# 5. Unit Testing
Every unit test should verify a single behaviour.
Examples:
- Utility functions - Custom hooks - React components - Validation schemas - Services - Recommendation scoring - Helper functions
Unit tests should not require a database or network.
---
# 6. Integration Testing

Integration tests verify interaction between modules.
Examples:
- API  Database - Controller  Service - Service  Repository - Authentication middleware - Prisma integration - Cloudinary provider (mocked) - AI provider abstraction (mocked)
---
# 7. End-to-End Testing
Critical user journeys must be tested.
Examples:
- Register account - Login - Complete onboarding - Search for books - Add a book to library - Update reading progress - Write a review - Follow another reader - Join a book club - Send a message - Join a video discussion - Logout
E2E tests should reflect real user behaviour.
---
# 8. API Testing
Every endpoint must verify:
- Success responses - Validation failures

- Authentication - Authorization - Rate limiting - Error handling - Edge cases
---
# 9. AI Testing
The AI layer should be tested independently.
Verify:
- Prompt generation - Provider abstraction - Recommendation ranking - Fallback behaviour - Error handling - Response parsing - Caching
AI providers should be mocked during automated tests.
---
# 10. Real-Time Testing
Verify:
- Socket authentication - Room joining - Presence updates - Message delivery - Read receipts - Reconnection - WebRTC signalling
Real-time tests should cover both success and failure scenarios.
---
# 11. Database Testing

Verify:
- Prisma models - Relations - Constraints - Index usage - Soft deletes - Transactions (if introduced) - Data integrity
Tests should use an isolated test database.
---
# 12. Component Testing
Reusable UI components should verify:
- Rendering - User interactions - Keyboard navigation - Accessibility - Loading states - Error states - Responsive behaviour where applicable
---
# 13. Accessibility Testing
Verify:
- Keyboard navigation - Focus management - Colour contrast - ARIA labels - Screen reader compatibility - Semantic HTML
Target WCAG 2.2 AA compliance.
---
# 14. Performance Testing

Monitor:
- Initial page load - API latency - Search response time - Recommendation generation - Bundle size - Largest Contentful Paint (LCP) - Interaction to Next Paint (INP) - Cumulative Layout Shift (CLS)
---
# 15. Security Testing
Verify:
- Authentication - Authorization - Input validation - JWT handling - Rate limiting - File upload restrictions - XSS protection - Injection resistance
---
# 16. Regression Testing
Every resolved bug should include:
- A regression test - Documentation of the root cause - Verification that similar behaviour is protected
---

# Purpose
Architecture Decision Records (ADRs) document important technical decisions made during the development of BookHive.
Each ADR answers:
- What decision was made? - Why was it made? - What alternatives were considered? - What are the consequences?
ADRs are permanent historical records.
Once accepted, an ADR should not be edited significantly. If a decision changes, create a new ADR that supersedes the previous one.

Every file should feel like it was written by the same engineering team. Consistency, simplicity, and maintainability always take precedence over clever or overly complex solutions.
I want to introduce a Recommendation Engine Pipeline that separates AI from recommendation logic. Instead of the application asking Grok directly for recommendations, the flow should be:
User Activity  
Behaviour Tracker  
Recommendation Engine   Content-Based Engine  Collaborative Engine  Popularity Engine  Freshness Engine  AI Reasoning Engine  
Ranking Engine  
Recommendation Feed
This has several advantages:
 The application still provides high-quality recommendations even if the AI provider is unavailable.
 AI enhances recommendations rather than replacing established recommendation techniques.

 New recommendation strategies can be added without changing the rest of the system.  The recommendation engine remains testable and deterministic where appropriate.
This hybrid architecture is much closer to how production recommendation systems are built, and it will make BookHive a significantly stronger engineering project.
Instead of placing all Socket.IO logic in a single socket.ts file, organise it as feature modules:
backend/  src/
 realtime/  index.ts  socket.ts  middleware/   authenticate.ts   rateLimit.ts  events/   chat.events.ts   club.events.ts   notification.events.ts   presence.events.ts   video.events.ts  services/   presence.service.ts   room.service.ts   messaging.service.ts  types/
Benefits:
 Clear separation of concerns.  Easier testing of individual event handlers.  Simpler maintenance as real-time features expand.  Better scalability when introducing additional event types.
